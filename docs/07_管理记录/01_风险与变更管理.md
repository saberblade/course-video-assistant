# 风险与变更管理

版本：V1.1。维护人：PM。风险预案已编制，分工和技术路线已确定；运行风险尚未经过实机验证，不表示已经发生故障。展示相关风险暂缓。

## 处理原则

由最接近问题的角色提交证据，PM判断对范围、节点和展示的影响。技术问题由BE/SYS/FE提出可行方案，QA说明测试影响。变更涉及基线时同步修改[统一约定](../00_项目导航与统一约定.md)，避免实现、测试和展示各用一套口径。

阻塞预计超过半个工作日，或将影响下一里程碑时，主责人及时通知PM和直接依赖人。密钥、数据或结果正确性问题立即处理。风险优先级是项目判断，不能当作发生概率的统计结果。

## 风险更新方式

风险状态使用：待验证、预防中、已发生、处理中、已缓解、已关闭、暂缓。关闭需说明证据和残余影响；暂缓不等于已解决。模型、环境或样本变更后，原关闭结论可能失效，须重新检查。

## 需求变更流程

1. 提出人写明原需求、新需求、原因，以及不改会有什么影响。
2. FE/BE/SYS评估实现工作量与依赖，QA评估测试和数据影响，PM评估用户价值与节点。
3. PM作出接受、延后或拒绝决定。涉及预算与学校要求时记录确认依据，不自行推定外部规则。
4. 接受后更新基线、PRD、接口、任务与用例，并通知接收人重新确认。
5. 完成实现和回归后关闭变更。范围决定与实现完成分别记录。

M3后默认只接收阻断/严重缺陷修复和必要合规/数据处理修正。P1体验功能留到后续版本。

## 需要记录的典型变更

- small改为base或更换转写方案：可能改变准确性与性能，需QA复测。
- qwen-plus或地区端点变化：需重新验证鉴权、响应与费用控制。
- 文件大小/时长上限、队列数、超时修改：影响前后端校验与边界用例。
- 删除或重试策略、时间字段、API包装变化：影响已有数据与多方实现。
- 验收门槛变化：必须保留原门槛、理由与实际结果，不能为了掩盖失败而降低统计要求。
- 展示日期变化：同步M4/M5、演示设备与成员在场安排。
